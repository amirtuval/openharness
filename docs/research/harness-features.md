# Harness feature inventory

_A survey made on 2026-10-01 to plan the roadmap. Moved here from a GitHub issue; see [ROADMAP.md](../ROADMAP.md) for the plan and its order. Claims marked unverified are leads to check, not facts._

A feature-by-feature inventory of five agent harnesses, mapped to openharness's v1 scope (chat-only, durable Postgres event log, stateless brain, pluggable hands) and its chosen roadmap order: **authentication → deployment/CI-CD → model selection with API keys → tools**.

Harnesses compared:

- **CC** — Claude Code (Anthropic's terminal agent)
- **MA** — Claude Managed Agents (the server-side architecture openharness is modelled on)
- **OC** — OpenCode (open-source terminal agent)
- **Cx** — Codex (OpenAI's CLI + app-server)
- **pi** — pi coding agent (earendil-works)

Legend: **✓** supported · **~** partial / indirect / undocumented · **—** absent. "openharness relevance" is H/M/L with a short reason. MA entries quote exact event/resource names.

## 1. Conversation core

How each harness puts persistent knowledge into context, how it compresses context as the window fills, and how users see/restore what's there.

## Design ideas worth borrowing

- **Vaults + egress substitution (MA, §11/§5).** Per-user credential collections referenced by `vault_ids` at session creation; `environment_variable` credentials sit in the sandbox as an opaque placeholder and are substituted at egress, scoped by `injection_location` and per-credential `allowed_hosts` — "secrets never enter the sandbox," with documented caveats (SigV4-style signing, token-exchange flows).
- **Budgets as a first-class field, with `session.usage` (§11).** `budget.max_list_cost` (whole cents as a string), enforcement _between_ model requests, pause-not-terminate on `stop_reason: budget_reached`, only settle events accepted at the cap, a `session.usage` snapshot before every idle, and one shared cap across multi-agent threads.
- **Outcomes: "done" as a gradeable event (§12).** `user.define_outcome` with a required rubric, a grader running in a separate context window, `span.outcome_evaluation_start/_ongoing/_end` with `satisfied`/`needs_revision`/`max_iterations_reached`/`failed`/`interrupted` and an iteration counter. Arguably the single best idea in the inventory for a durable-log harness.
- **pi's steering vs follow-up queues (§1) and the session tree (§9).** Steering enters after the current assistant turn; follow-ups after all pending work; abort returns queued messages to the editor. The session file is an append-only entry tree with `CompactionEntry.firstKeptEntryId`, `branch_summary`, and append-only `context_edit` entries — compaction and edits as events, never mutations.
- **CC's hook pipeline (§7).** ~35 lifecycle events (PreToolUse, PermissionRequest, SessionStart, PreCompact, WorktreeCreate…), three-tier config with matchers, five handler types (`command`/`http`/`mcp_tool`/`prompt`/`agent`), exit-0 stdout-JSON vs exit-2 blocking semantics, and `additionalContext` injection.
- **Codex app-server's embedding + replay rules (§10/§9).** JSON-RPC with a capability handshake (`initialize`, `experimentalApi`), explicit `historyMode` that _fails closed_ when paginated history isn't supported, and `turn/steer` requiring `expectedTurnId` — optimistic concurrency for steering a live turn.
- **OpenCode v2's durable-event discipline (§9).** Durable DB rows are authoritative and wakeup-only live events are never replayed; `event.durable` gates the reconnect cursor; prompt input is split into `admitted` vs `prompted`; history paginates after an exclusive aggregate sequence with `hasMore` and allowed gaps. (Source-derived; "divergence detection" per se was not found documented.)
- **Preview vs authoritative reconciliation (§1).** MA ships best-effort `event_delta` previews that may be shed under load, with the buffered `agent.message` as the only truth, reconciled by matching IDs and closed at `span.model_request_end` — the exact recipe for openharness's SSE reconnects.
- **Permission decisions as auditable events (§6).** Every MA tool event carries `evaluated_permission` plus an `evaluation` object naming the policy and, under `auto`, a `reason_code` (`high_risk`, `indeterminate`). Plus the intent rule: only `user.message` counts as user intent; tool results and fetched content are assessed but never obeyed.
- **Environments as resources, work as a queue (§5).** `environment` is a versioned-less resource (keep your own change record) that sessions reference; self-hosted mode turns it into a work queue with an always-on or webhook-triggered worker, and memory stores sync on an interval with store-wins conflict resolution.
